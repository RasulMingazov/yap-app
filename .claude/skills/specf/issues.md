# Spec-first: известные проблемы и предложения

Заметки по итогам ревью текущего spec-first воркфлоу (`.claude/skills/specf/`, команды `specf-*`,
агенты `specf-coordinator`/`specf-worker`). Ничего из перечисленного ниже ещё не применено — это
список находок и предложений для будущей правки.

## 1. Стоимость чтения контекста

Каждая команда обязана прочитать `SKILL.md` целиком плюс «all feature artifacts». Для фичи
`001-authentication` это `spec.md` (699 строк) + `plan.md` (742) + `tasks.md` (300) = ~1750 строк
на каждый вызов, до чтения кода. На практике это видно по расходу токенов параллельных воркеров —
~76.9k и ~75.7k токенов на подзадачи вроде «grep требований» и «список Gradle-тасков», хотя сами
подзадачи тривиальны.

Причина: `specf-worker.md` предписывает «Read the assigned artifacts» без уточнения объёма, из-за
чего воркер, вероятно, перечитывает файлы целиком вместо выданной координатором выдержки.
`specf-coordinator.md` уже требует передавать «exact feature, phase, task IDs, allowed paths,
required baseline, and focused verification commands», но не требует вставлять сам текст задач и
требований в промпт воркера — только ссылки на них.

### Предложение (план сокращения стоимости без потери точности)

1. **Инлайн выдержки от координатора.** Координатор вставляет в промпт воркера точный текст
   назначенных задач из `tasks.md` и текст только тех `R-`/`AC-` ID, которые к ним относятся —
   вместо того чтобы отправлять воркера читать `spec.md`/`plan.md` целиком. Воркер лезет в полный
   файл только если встретил ссылку на ID, которого нет в выдержке. Это самый дешёвый вариант —
   ноль дополнительных вызовов инструментов на поиск.
2. **Скоуп по границам секций, а не по фиксированному окну строк.** Когда всё же нужен point-lookup
   (например, в `specf-verify`), извлекать секцию по заголовкам markdown:
   `sed -n '/^### R-042/,/^### /p'` — точная граница раздела, один вызов, без обрезки/лишнего.
   Родной Grep-тул с `-C`/`-A` context тоже подходит (один вызов вместо grep+Read), но у него
   фиксированная ширина контекста, поэтому границы по заголовку точнее.
3. **Лёгкий скрипт статуса** (`.claude/skills/specf/scripts/status.sh`, по образцу
   `check-prerequisites.sh`/`common.sh` из истории репозитория, коммит `09c746a`, до перехода на
   spec-first в `cb84aa8`) — отдаёт JSON: какие файлы есть, какие task ID не закрыты и по каким
   фазам, HEAD, git status. `specf-parallel`/`specf-verify` используют его вместо полного чтения
   `tasks.md` ради «reconcile task markers in memory».
4. **Полное чтение оставить только там, где точность критична**: авторинг `spec`/`plan` и финальный
   `verify`. Ослаблять только повторяющийся горячий путь параллельных воркеров и readiness-проверок.

Идеи 1–3 частично вдохновлены старым Spec Kit, который стоял в этом репозитории до spec-first
(`.specify/` в `09c746a`): там бухгалтерия состояния считалась скриптом и отдавалась агенту готовым
JSON, а не вычитывалась заново каждый раз. Возвращаться к файловому дроблению Spec Kit
(`research.md`, `data-model.md`, `contracts/*.md`) не стоит — от него в проекте осознанно ушли
ради простоты (`cb84aa8`, `0490443 Remove separate project principles`).

## 2. Разрастание артефактов

Шаблоны компактные (`spec-template.md` — 45 строк, `plan-template.md` — 42, `tasks-template.md` —
15), но реальные артефакты фичи вырастают в 15–16 раз (699 / 742 / 300 строк). Есть прямое
дублирование содержимого: например «T-ID scaffold» описан трижды — в Requirements, в Acceptance
criteria и в Plan. Каждая лишняя строка в `spec.md`/`plan.md` — это лишние токены на каждое будущее
чтение всеми командами.

Предложение: свести повторяющиеся темы к одному месту с явной перекрёстной ссылкой; добавить в
`spec-template.md`/`plan-template.md` мягкий ориентир по размеру (например, ~400 строк на раздел —
дальше стоит выносить неблокирующий скоуп в отдельную последующую фичу).

## 3. Владение путями — только на уровне промпта

Правила «coordinator owns `specs/**` и `.claude/**`», «worker must not touch coordinator-owned
paths» нигде не проверяются автоматически, только текстом инструкции. Для сравнения — pre-push хук
Detekt в этом репозитории (`.githooks`) — настоящий automated guard rail; для path ownership в
spec-first такого нет. Риск: под сложной задачей агент может случайно выйти за границу владения,
и это заметят только на ревью диффа.

## 4. Именование агента в UI не соответствует доменной роли

`specf-parallel.md` требует давать воркерам доменные роли («role name based on its module and
concern, such as `server-auth`, `mobile-auth`»), но реальный `subagent_type` всегда `specf-worker` —
это следствие того, что на `main` есть только один универсальный агент-воркер (см. синхронизацию
`feature/login`, где были удалены `specf-backend.md`/`specf-mobile.md`, отсутствовавшие на `main`).
В сайдбаре/UI виден только `specf-worker`, доменная роль — исключительно в тексте отчёта
координатора. Механизм субагентов Claude Code не поддерживает alias/display-name отдельно от
`subagent_type`, так что это ограничение самого инструмента, а не документа. Единственный способ
показать доменное имя в UI — завести отдельные именованные агент-файлы под каждый домен, что снова
разойдётся с `main` (сознательно решили не делать).

## 5. Нейминг команд

- `specf-spec` — тавтология (spec + spec), единственная команда-существительное на фоне
  `plan`/`implement`/`verify` (все — действие). Оригинальный Spec Kit называл этот шаг
  `/speckit.specify`. Предложение: `specf-specify` или `specf-define`.
- `specf-parallel` — вводит в заблуждение по смыслу: команда не всегда параллелит, при
  `NOT READY` она честно предлагает один последовательный пакет как fallback. Имя обещает то, чего
  команда не всегда делает. Предложение: `specf-batch` или `specf-dispatch` — «собрать и запустить
  следующий безопасный кусок работы, параллельно если можно».
- При переименовании нужно синхронно поправить упоминания в `SKILL.md`, `specf-coordinator.md`,
  README и `argument-hint` — иначе появится рассинхрон в документации.

## 6. `specf-verify` не оставляет следа

Намеренное решение — не создавать «verification reports» — держит репозиторий чистым, но лишает
командную работу аудиторского следа: после чата не остаётся записи, кто и когда подтвердил
`OVERALL: PASS`. Для одиночной работы это не проблема; при командной работе или ревью PR может не
хватать этой истории. Изменение — компромисс, а не однозначный баг; фиксирую для обсуждения.

## 7. Параллелизация — фиксированный потолок без учёта размера пакета

Максимум 2–3 воркера с изоляцией через worktree — разумно для конфликтов, но для мелких
однофайловых фаз накладные расходы на создание/очистку worktree и полное чтение артефактов могут
превышать выгоду от параллельности. Возможная эвристика: не распараллеливать пакет, состоящий из
одной задачи.

## 8. `NEXT` — текст вместо интерактивного выбора

`SKILL.md` заканчивает каждую успешную операцию блоком `NEXT` с одной copy-ready командой
(`/specf-implement 001-authentication --phase 4`), которую нужно скопировать и вставить вручную.
`specf-parallel.md` при этом уже требует интерактивного подтверждения через question tool
(`Run`/`Change`/`Cancel`) для запуска батча. `NEXT` стоило бы привести к тому же паттерну —
интерактивный выбор («Apply `/specf-implement 001-authentication --phase 4`», «Change», «Skip» и
т.д.) вместо текстовой команды, которую нужно копировать руками. Особенно заметно там, где после
`NEXT` есть реальная развилка (например, продолжить фазу 4 последовательно или сначала проверить
через `/specf-parallel`, независима ли фаза 4 от фазы 6, как раньше были независимы фазы 3 и 5).

## Статус

Ничего из пунктов 1–8 не применено. Список — основа для отдельных точечных правок по каждому пункту.
